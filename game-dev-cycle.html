Reference — Production Pipeline

The Game Development Cycle

How a game moves from an idea to a shipped, patched, live product — the design work, the task breakdown, the writing, the code, the review, and the testing that turns a pitch into something players can run.

01

Concept & Pitch

Before there's a plan, there's a bet worth making

Someone — a director, a designer, sometimes the whole studio in a jam — writes a one- or two-page pitch: the core fantasy, the genre comparison ("it's X meets Y"), why it's fun, and why now. For funded studios this goes to leadership or a publisher for greenlight; for indies it's the filter that decides what gets a prototype.

Output

  • Pitch deck / one-pager — hook, audience, comparables, scope estimate
  • Vertical slice target — the single scene or loop that proves the fantasy
  • Risk list — the two or three things that could kill the project technically or creatively
02

Game Design

Turning a fantasy into systems, rules, and a document people can build from

Designers break the pitch into mechanics: core loop, progression, economy, controls, level structure. This is where prototyping happens — grey-box levels, spreadsheet economies, paper mockups — to test whether the fun actually holds up before a single production asset gets built. The output is the Game Design Document (GDD), though most modern teams keep it as a living wiki rather than a static PDF, since it changes weekly through the whole project.

Design artifacts

  • Core loop & pillars (3–5 things the game is always true to)
  • Systems specs — combat, economy, AI, progression
  • Level & encounter briefs
  • UX flows and menu wireframes

Who's involved

  • Game / systems designers
  • Creative director (holds the pillars)
  • Technical director (feasibility pass)
  • Lead artist (visual target)
03

Planning & Task Breakdown

The point where design intent becomes tickets someone can pick up

A design doc isn't actionable until it's decomposed. Producers and leads turn each system or feature into epics, then into scoped tickets small enough to estimate and finish inside a sprint or milestone — usually a day to a week of work each. This is also where dependencies surface: a combat ability ticket blocks on an animation rig, which blocks on a character being approved in art review.

Games commonly run on a hybrid cadence: Scrum-style sprints for engineering and tools work, and milestone/Kanban flow for content and art, since art and level work rarely fits a clean two-week box.

A well-formed ticket

  • Context — link to the GDD section or design brief it implements
  • Acceptance criteria — the observable behavior that makes it "done"
  • Scope — one feature slice, not "implement inventory system"
  • Dependencies — assets, other tickets, or design decisions it's blocked on
  • Owner and estimate
04

Content & Narrative Writing

Story, dialogue, and text run their own pipeline alongside code

Narrative designers and writers work from the same GDD pillars but on their own track: story outline → beat sheet → script draft → editorial pass → implementation into the engine's dialogue or quest system. Because writing has to survive contact with systems (branching dialogue needs to actually branch in the tool, barks need to fit in a text box, VO needs a recording pass and lip-sync), writers work tightly with the tools/UI programmer who owns the narrative pipeline.

Writing pipeline

  • Outline & character bibles
  • Beat sheets reviewed by design + narrative director
  • Script draft in a dialogue tool (Yarn Spinner, ink, articy:draft, or custom)
  • Editorial / continuity pass
  • VO recording, localization hand-off, in-engine implementation

Watch for

  • Text length vs. UI space and subtitle timing
  • Localization string IDs set up before, not after, writing
  • Branch state tracked so QA can actually test all paths
05

Production — Writing the Code

Engineers pick up tickets and build the systems designers specified

Each engineer branches off the mainline, implements the ticket's acceptance criteria, and works against the engine (Unity, Unreal, Godot, or in-house) plus whatever automated tests exist for that system. Games differ from most software here in two ways: binary, un-mergeable assets (scenes, textures, audio) push many studios toward trunk-based development with file locking (Perforce is still dominant for this reason) rather than long-lived Git feature branches; and a build has to actually run on target hardware, so engineers are checking frame time and memory budget as part of "done," not just logic correctness.

Day-to-day loop

  • Pick up ticket → sync latest → branch or lock files
  • Implement against acceptance criteria
  • Local test in editor + on target platform/devkit
  • Write or update automated tests where the system allows it
  • Open PR / changelist for review

Continuous integration

  • Automated build on every merge (often per-platform)
  • Smoke tests + unit tests gate the merge
  • Nightly full builds distributed for playtesting
  • Static analysis / lint for engine-specific gotchas
06

Pull Requests & Code Review

A second set of eyes before anything reaches the mainline

Review in games covers more than diff-reading: reviewers often need to pull the branch and run it, since a logic change can be correct on paper and still break at 30fps under load, or read a physics tuning value that's clearly wrong only when you see it move. Non-programmer reviewers (design, art) may sign off on their own domain — a designer approving a tuning change, an artist approving a shader — separate from the technical approval.

Typical review checklist

  • Meets the ticket's acceptance criteria, nothing extra sneaked in
  • Runs in editor and on a target build, not just "works on my machine"
  • No obvious perf regression — profiler check for hot-path changes
  • Tests added or updated where the system supports it
  • No orphaned assets, debug logging, or commented-out code left in
  • Naming and structure match the project's conventions

07

QA & Bug Testing

Where "it compiles" turns into "it's actually fun and doesn't crash"

Game QA runs on several tracks at once, because no single method catches everything: automated tests catch regressions fast but can't judge feel; scripted test passes catch known-risk areas methodically; and exploratory/playtesting is what actually finds the bugs nobody thought to write a test for.

Testing types

  • Unit / integration tests — engineering-owned, run in CI
  • Smoke tests — does the build boot, load a level, not crash in 5 minutes
  • Scripted test passes — QA follows a written test plan per feature
  • Exploratory / ad-hoc — QA tries to break it, no script
  • Playtesting — internal or external players judge feel, difficulty, clarity
  • Regression pass — re-verify previously fixed bugs before each milestone
  • Soak / stability tests — long-run sessions for memory leaks and crashes
  • Cert / compliance testing — platform holder requirements before submission

Bug lifecycle

Reported→ Triaged→ Assigned→ Fixed→ Verified→ Closed

A good report has repro steps, expected vs. actual behavior, build number, and — ideally — a video clip. Triage sets severity (crash/blocker → minor/cosmetic) and priority separately, since a common cosmetic bug can outrank a rare crash.

08

Build, Certification & Release

Alpha, beta, gold — and the platform holder's own gate

As the project matures, milestones tighten: alpha (feature complete, still buggy), beta (content complete, stabilizing, feature-frozen), code freeze (bug fixes only), gold / RC (release candidate). Console platforms (PlayStation, Xbox, Switch) add a formal certification pass against their technical requirements checklist — save handling, suspend/resume, controller disconnect behavior, age rating compliance — which can bounce a submission back if failed. PC releases go through storefront review instead (Steam, Epic), which is lighter but still has content and functionality checks.

09

Live Ops & the Loop Back

Shipping isn't the end of the cycle — it's where the loop starts feeding itself

Post-launch, telemetry and player feedback become design input: retention curves, crash reports, community bug threads, and balance complaints all turn back into new tickets, which go through the same design → task → write/code → review → QA loop as everything before launch — just faster, and against a live audience. Patches, seasonal content, and balance passes run this loop indefinitely for live-service games; smaller or narrative titles run a shorter tail of day-one patches and then wind down.
